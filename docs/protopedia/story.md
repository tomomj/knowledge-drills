## ドキュメントにも DevOps を

コードには DevOps があります。テストが落ちれば気づけますし、エラー率が上がればアラートが飛びます。
壊れたことを観測して、直して、デプロイする。このループは、今では当たり前になっています。

一方で、研修資料やオンボーディングドキュメントはどうでしょうか。
内容は少しずつ現状とずれ、説明が足りない場所では、新しい読者が何度も同じつまずきを繰り返します。

それでも作者には、テスト失敗もアラートも届きません。**「読者がどこでつまずいたか」を知るためのテレメトリがない**からです。
どこを直すべきかも、直した結果がよかったのかも、勘と個別の聞き取りに頼るしかありません。

Knowledge Drills は、この「観測できないドキュメント」に DevOps のループを持ち込むアプリです。

> **受講者のつまずきをテレメトリにして、教材が自分で改善案を出します。**

![受講者の誤答から AI が文書改善パッチを作り、人間が承認するループ](../images/knowledge-drills-feedback-loop.png)

## 何ができるのか

Knowledge Drills は、Markdown の教材からドリルを作り、受講者の誤答から教材の改善パッチを提案するアプリです。
問題を作って終わりではなく、修正後の回答結果まで観測し、教材を継続的に改善します。

具体的には、次のループを回します。

1. Markdown の教材から、根拠付きのドリルを生成
2. 受講者の回答を AI が採点
3. 未分析の回答が閾値に達すると、**エージェントが自動で分析を開始**し、教材の説明不足を特定
   （閾値はデモ用に 3 件へ設定。少人数でも改善サイクルが体験できるようにするため）
4. Markdown の改善パッチを提案
5. 人間がパッチを適用または却下
6. 次の回答結果から、改善効果を確認

分析の起動に人間の操作は要りません。回答が集まると、エージェントが自分で動き出します。
ただし教材を変更できるのは人間の承認だけです（後述の 3 つのルール）。

![講座一覧。各講座のスコア推移と、「AIの改善案あり」の状態が一目で分かる](../screenshots/10-course-list-dashboard.png)

RAG が「ドキュメントを使って回答する」仕組みなら、Knowledge Drills は**ドキュメント自体を改善する**仕組みです。
コードの DevOps と対応させると、次のようになります。

| DevOps | Knowledge Drills |
|---|---|
| コード | 教材 Markdown |
| テレメトリ | 受講者の誤答 |
| 障害分析 | AI による誤答分析 |
| 修復 PR | Markdown パッチ |
| レビュー・デプロイ | 人間による承認・適用 |
| 改善確認 | バージョンごとの平均スコア |

## 安全に改善するための3つのルール

AI が教材を扱うからこそ、もっともらしい問題や修正案をそのまま通さない仕組みが必要です。
Knowledge Drills では、次の3つを境界にしています。

- **根拠のある問題だけを作る:** 設問が教材のどの記述に基づくかを保存し、Backend でも実在を検証します。
- **根拠の弱い分析を通さない:** 誤答を3つの視点で分析し、critic と reviewer が採否を確認します。
- **最後は人間が決める:** AI はパッチを提案するだけです。適用・却下は教材のオーナーが判断します。

![AIが根拠付きの改善パッチを提案し、人間が適用または却下する承認ゲート](../images/knowledge-drills-human-gate.png)

## デモで確認できること

「改善できそう」という主張だけで終わらないように、教材の欠落を見つけるところから、パッチ適用後の効果測定までをデモにしています。

## 実測ループの記録（審査期間中も更新されます）

上の経費精算講座は、改善ループを確実に再現するためのシードデータです。
ここからは、**実在する人の回答**で本番の改善ループが動いている記録です。

### 公開ドリルから実際のループに参加できます

題材は「そのだの取扱説明書 — 緑タイツ忍者が Knowledge Drills を作った話」です。
ログイン不要で、全 3 問を約 1 分で回答できます。

![受講者の回答画面。共有URLを開くと、ログイン不要で教材を読んでドリルに回答できる](../screenshots/11-learner-drill-share.png)

**[公開ドリルに回答して、実際の改善ループに参加する](https://knowledge-drills-prd-frontend-96923902284.asia-northeast1.run.app/drills/fB_WDuwHY9XPctBlt69gftD0EDDR8IGD1b8GNoH3g6c)**

ここで送信された回答は、本番環境のテレメトリとして蓄積されます。
未分析の回答が 3 件（デモ用の閾値設定）に達すると、エージェントが自動で分析を開始。
改善が必要な場合だけ教材のパッチを起案し、人間の承認後に次のバージョンへ反映します。
つまり、**このドリルへの回答が、次の改善ループを実際に動かします。**

### 実際に6人に使ってもらったら、改善ループが2回動いた

**2026-07-12 21:59 時点**の実測結果です。

| 教材 | 実回答 | 本番環境で起きたこと |
|---|---:|---|
| v1 | 3件 | 閾値到達でAIが自動分析し、最初の改善パッチを起案。人間が承認してv2へ更新 |
| v2 | 3件 | 再び閾値へ到達し、2回目の自動分析を実行。新しい改善案を起案し、人間の確認待ち |
| 合計 | **6件** | 実回答だけで1周目を完了し、2周目の改善提案まで到達 |

#### 1周目と2周目で、AIの診断が変わった

![本番Firestoreに保存された実回答3件ずつのFailure Signalから、1周目と2周目で変化したAIの診断を比較](../screenshots/17-production-analysis-rounds.png)

1周目では、v1への回答3件すべてから「設問の抽象度とRubricの厳密性の乖離」を検出しました。
受講者は内容を理解しているのに、Rubricが求めるキーワードを再現できず、形式的な減点が起きているという分析です。
そこで、誤答原因の分類プロセスを箇条書きで明示し、設問が意図する評価ポイントを構造化してv2を公開しました。

この改善案を画面で見て、僕自身も、文章として読んだだけで判断手順まで覚え、
回答するときに再現できる人は多くないだろうと感じました。
内容を増やすだけではなく、覚えて使える単位へ箇条書きにすること自体が、教材にとって重要な改善です。

#### 2周目では、回答の曖昧さを3つに分解した

v2への3件の回答を分析すると、AIは次の3つを共通のつまずきとして検出しました。

| 検出したつまずき | 該当 | 分析された原因 |
|---|---:|---|
| 回答の根拠提示不足 | 3 / 3件 | 公開情報に基づいて回答するというルールが教材末尾にあり、回答時に意識されにくい |
| 回答に含まれるべき詳細情報の欠如 | 3 / 3件 | 手順や判断プロセスの説明が概念的で、具体的な構造として再現しにくい |
| 設問要件の抽象性に起因する回答具体性の低下 | 3 / 3件 | 結論だけでなく、判断理由・根拠・分類手順まで書く必要があることが伝わっていない |

![教材v2への実回答3件すべてから検出された、根拠不足・詳細不足・設問要件の抽象性という共通のつまずき](../screenshots/16-production-second-analysis-signals.png)

3つに分かれていますが、まったく別の問題が現れたわけではありません。
1周目の「期待される回答が伝わっていない」という診断を、根拠提示・詳細情報・設問要件へ具体化した結果だと考えています。

#### 分析は広く、パッチは教材で直せる範囲に絞った

Firestoreに残った分析を見ると、AIが見つけた問題と、実際に教材へ適用する変更は同じではありません。

| 周回 | 分析から導いた本来の改善案 | 教材Markdownのパッチで実施したこと |
|---|---|---|
| 1周目 | 設問を具体化する、またはRubricの完全一致条件を緩める | Rubric変更は対象外とし、分類プロセスの箇条書き化と評価ポイントの構造化に限定 |
| 2周目 | 回答項目を設問ごとに明示し、根拠の引用を必須にする | 設問は教材構造の対象外とし、共通の根拠提示ルールを冒頭へ移動。判断プロセスも具体化 |

つまり、分析では教材・設問・Rubricを横断して原因を探しながら、パッチでは教材Markdownだけを安全に変更しています。
検出した問題を無理にすべて教材へ書き足すのではなく、変更できない範囲を明示して人間の判断へ残す設計です。

#### この実測で確認できたこと

今回、シードデータではなく実回答を入力として、
**自動分析 → 改善案 → 人間の承認 → 再配布 → 再分析**が本番環境で連続して動くことを確認しました。

一度の修正で終わらず、改善後にも残ったつまずきを次のテレメトリとして扱い、再び改善へつなげられる。
今回の実測によって、Knowledge Drillsが目指す「生きているドキュメント」のループを実際に示せました。

## おわりに

> **つくる → まわす → つまずきを見つける → 直す → 効果を確かめる**

Knowledge Drills は、この DevOps ループをナレッジにも持ち込みます。
