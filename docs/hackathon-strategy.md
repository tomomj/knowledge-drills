# DevOps × AI Agent Hackathon 2026 優勝戦略

Status: Draft v0.1（2026-07-05）
対象: [DevOps × AI Agent Hackathon 2026](https://findy.notion.site/devops-ai-agent-hackathon-2026)

## 0. ハッカソン要点

- **テーマ**: 「つくる、まわす、とどける」— AIエージェントの企画→開発→CI/CD→本番デプロイ・運用
- **審査基準（5項目）**:
  1. AIエージェントが価値の中心か
  2. 課題へのアプローチ力と新規性
  3. ユーザビリティの直観性
  4. 実用性と体験価値
  5. 実装力と拡張性
  - 加えて「エージェントとしての必然性」「自律的に判断しタスクを実行する設計」が強調されている
- **必須要件**: Google Cloud アプリ実行基盤（Cloud Run 等）+ Google Cloud AI（Gemini API 等）
- **提出物**: 公開 GitHub リポジトリ URL / デプロイ済み URL / Proto Pedia 登録
- **締切: 7/10**（時刻は公式 Notion で要確認。connpass には 7/10 10:00 の記載あり）
- 一次・二次審査は**提出物のみ**で判断される。ピッチ（8/19 最終、Google 渋谷オフィス）は最終選出後

## 1. 大前提

一次・二次は「審査員が一人で触って、3分で価値を理解できるか」がすべて。
したがって手順は「機能を作る順」ではなく「**審査員の体験を設計する順**」で組む。

### エージェント構成の方針（決定済み）


4つの固定スキーマエージェントを **3つに削減**し、1つを完全自律型にする。

1. `drill_generator_agent` — 固定スキーマ（現状維持）。出力の信頼性が命
2. `grading_agent` — 固定スキーマ（現状維持）。採点がブレたら受講者体験が壊れる
3. **`improvement_agent`（新・自律型）** — `failure_analysis_agent` + `document_patch_agent` を統合。
   ツールを持ち、証拠を集め、「パッチを出す／出さない」を理由付きで判断し、起案までする

> 「信頼性が要る所は決定的に、判断が要る所は自律的に」という使い分けが
> 審査基準「エージェントとしての必然性」への直接の回答になる。
> 「4つのLLM呼び出しを3つに減らして、1つを本物のエージェントにした」という削った話がそのままストーリー。

**ADK 実装上の注意**: `output_schema` を設定したエージェントはツールが使えない。
自律化するエージェントは `output_schema` を外してツール
（`get_course_markdown` / `get_grading_history` / `get_patch_history` 等）を持たせ、
最終出力の JSON 検証は backend 側の境界（Pydantic）で行う。

## 2. コンセプト（一撃の一文）

> **「書いた瞬間から腐っていくドキュメントに、DevOpsを。受講者のつまずきをテレメトリとして、資料が自分で改善プロポーザルを出す」**

- キーワードは「**自己改善するドキュメント**」
- RAG（ドキュメントを使ってAIが答える）の**逆張り**＝「AIがドキュメント自身を直す」
- README 冒頭・Proto Pedia・デモ動画の1カット目、すべてこの一文で統一する

### 審査基準への対応マップ

| 審査基準 | このプロダクトの回答 |
|---|---|
| ① Agentが価値の中心か | 改善Agentが証拠を集め「直すか・直さないか」まで自律判断。人間はレビューのみ |
| ② アプローチ力と新規性 | 「答えるAI(RAG)」の逆張り＝「資料自身が改善されるAI」。3エージェント構成にあえて削った設計判断 |
| ③ ユーザビリティ | 講座一覧＝改善ループのダッシュボード、share URL だけで受講者参加 |
| ④ 実用性と体験価値 | 企業研修・オンボーディングの実課題。改善効果を数字で証明（スコア推移） |
| ⑤ 実装力と拡張性 | schema 検証境界、ガードレール、テスト、eval ゲート付き Agent CI/CD、Cloud Run + Firestore |

## 3. 手順（7/5 → 7/10）

### Step 1: コンセプトを一文に固める（7/5、30分）

上記の一文を確定し、全提出物で統一する。

### Step 2: デモ台本を先に書く（7/5-6、機能実装より先）

**Demo-driven development**。3分の台本を先に確定し、そこに映らない機能は作らない。

| 時刻 | シーン |
|---|---|
| 0:00 | **課題**: 実在感のある研修資料（例: 経費精算の判断基準）。「この資料、どこが分かりにくいか作者は知る術がない」 |
| 0:30 | **つくる**: 資料からドリル3問生成、share URL で受講者が回答（早送り） |
| 1:00 | **まわす（勝負の1分）**: 改善Agentの自律調査タイムライン。「採点履歴を分析中… §判断基準を読解中… 過去に却下されたパッチを確認し、同じ提案を回避… 例外条件の記載不足と特定」→ 根拠付きパッチ提案 |
| 2:00 | **人間がレビューして apply**（diff 画面。ガードレールの証明） |
| 2:30 | **クライマックス**: 再ドリルの平均点グラフが 2.1 → 3.4 に上昇。「資料の改善が、数字で証明された。これがナレッジのCI/CDです」 |

**最後の上昇グラフが最重要ショット。改善効果を定量で閉じるチームはまずいない。**

### Step 3: 台本から逆算した機能だけを深掘る（7/6-8）

優先順:

1. **スコア改善メトリクス**（④実用性の証明）
   - drill run 間の平均点比較。折れ線グラフ1本でいい。凝らない
2. **自律調査タイムライン**（①Agent中心の証明）
   - 改善Agentのツール呼び出しと判断を UI にストリーム表示
   - 「今回はパッチ不要と判断（理由: サンプル1件では資料起因と断定できない）」という**見送り判断**を必ず入れる
   - 「何でも提案する bot」と「判断する Agent」の違いが一番出る場面
3. **却下履歴からの学習**（②新規性の核）
   - 改善Agentが過去の却下パッチとその理由を読み、提案を変える
   - 「人間のフィードバックで賢くなる Agent」は審査員エンジニアに一番刺さる深掘り
4. **自律トリガー**
   - 回答が N 件溜まったら Agent が自分で分析を開始し、オーナーに「Agentからの提案が届いています」通知
   - 「人間がボタンを押すツール」→「勝手に働き、承認だけ求める Agent」への格上げ

### Step 4: 審査員の60秒導線を作る（7/9）

- **デモモード講座をプリロード**: デプロイ URL を開いた審査員が、回答データ投入済みの講座で
  「分析実行 → Agent の思考を眺める → apply → スコア改善」を自分の手で2分で体験できる状態にする
- **README**:
  - 冒頭にヒーロー GIF（タイムライン → グラフ上昇）
  - 一文コンセプト
  - アーキ図（Cloud Run / Firestore / CI/CD の eval ゲートを明示）
  - 「なぜ 4→3 にエージェントを減らしたか」の設計判断セクション（⑤実装力への強い答え）
  - 「なぜ Agent Engine ではなく in-process ADK Runner か」の設計判断
    （デプロイ単純性と同期呼び出し要件。invoker は `agent_mode` で差し替え可能な抽象であり、
    スケール時は Agent Engine へ移行可能 — 拡張性の証明として書く）
- **Proto Pedia + デモ動画（3分）**: Step 2 の台本をそのまま録画。ライブデモが壊れた時の保険も兼ねる

### Step 5: 模擬審査で磨く（7/9）

- 同僚1〜2人に審査基準5項目の表を渡し、**何も説明せずデプロイ URL と README だけ**見せて採点してもらう
- 「どこで理解に詰まったか」だけ聞いて直す
- 想定問答（1つだけ準備）:
  - Q: 「これ LLM パイプラインでは？」
  - A: 「調査経路が症状ごとに変わる・出さない判断がある・却下から学ぶ。この3つはワークフローでは書けない」

## 4. 前提タスク（土俵に乗る / 別途対応）

戦略の前提となる基盤作業。**7/8 までにずれ込むと敗北パターン**。

- [ ] 実 Agent 接続（現状 `backend/app/main.py` は `LocalAgentInvoker` スタブ。
      **ADK Runner in-process に決定、Agent Engine は使わない**（2026-07-07 決定。
      理由: 審査上の加点なし・提出物に映らない・デプロイ事故リスク増。
      invoker 抽象により将来の Agent Engine 移行パスは残る）
- [ ] 実 Firestore 接続（現状 `InMemoryFirestoreClient`）
- [ ] Dockerfile + Cloud Run デプロイ（backend / frontend）
- [ ] GitHub Actions で CD（「まわす」の証拠にもなる）
- [ ] Agent の CI/CD: CI に agent パッケージのジョブを追加（lint / typecheck / pytest。現状 CI 未収載）。
      余力があれば `adk eval` の小 evalset を cd.yml のデプロイ前ゲートに配置
      （WIF 認証は構成済みを流用。PR CI は認証情報なしを維持し、実モデル eval は main push 時のみ）

## 5. 負け筋チェックリスト

「絶対に勝つ」手順は存在しない。負け筋を全部潰し、
**「スコアが上がるグラフ」という他が持っていない1枚**を持ち込むのが最大化。

- [ ] 触れない（デプロイ URL が動かない / データが消える）→ 前提タスク + デモモード講座
- [ ] 伝わらない（README・Proto Pedia が3分で理解できない）→ Step 4
- [ ] ただのパイプラインに見える → タイムライン表示 + 見送り判断 + 却下学習
- [ ] 効果が主張止まり → Before/After スコアグラフ
- [ ] デモ事故 → デモ動画を保険に、シードデータで決定的に再現可能にしておく
